# CudaGauge — CPU/GPU Crossover Research & Benchmarking Library

## 1. Your role

Act as my senior C++/CUDA engineer and mentor. Build a complete, working project called **CudaGauge**.

CudaGauge is a reusable library and command-line tool that helps developers determine when their existing CPU implementation becomes slower than their CUDA GPU implementation.

The project investigates two approaches:

1. **Formula-based prediction:** Estimate the CPU/GPU crossover using a mathematical performance model fitted to a small number of measurements.
2. **Adaptive empirical benchmarking:** Discover the crossover through geometric sampling, targeted refinement, and repeated measurements.

We will compare both methods using actual benchmarks. If the formula works sufficiently well, it could power a lightweight threshold estimator. If it does not, the empirical approach should provide a more reliable alternative.

Do not assume either approach will win. The experimental results must determine the conclusions.

## 8. Two timing modes

Implement two distinct benchmark modes.

### Mode A: End-to-end execution

Compare CPU execution against GPU execution including the required host-to-device transfers, kernel execution, and result transfers.

Clearly document whether allocation and initialization costs are included.

The objective is to estimate when GPU offloading benefits the actual application.

### Mode B: GPU-resident execution

Assume the input data is already available in GPU memory.

Measure CPU execution against GPU kernel execution, with consistent handling of launch and synchronization overhead.

The objective is to estimate when GPU computation is worthwhile when data-transfer costs are not part of the operation.

Use `std::chrono` for CPU timing and CUDA events for GPU timing.

Perform appropriate synchronization so measurements represent completed work.

Separate one-time CUDA initialization and warm-up from normal execution.

Never compare results obtained using inconsistent timing definitions.

## 10. Formula-based predictor

Investigate this simple performance model:

\[
T_{\mathrm{CPU}}(N)=a+bN
\]

\[
T_{\mathrm{GPU}}(N)=c+dN
\]

Where:

- \(N\) is the workload size.
- \(a,c\) represent estimated fixed costs.
- \(b,d\) represent estimated per-unit costs.

When the denominator is nonzero, the predicted crossover is:

\[
N^*=\frac{c-a}{b-d}
\]

This is a hypothesis, not a guaranteed description of GPU performance.

Fit the model using a small set of calibration measurements. Prefer a simple, understandable least-squares implementation in ordinary C++.

If a simpler fitting method is used, document its trade-offs.

Handle cases where:

- The denominator is zero or nearly zero.
- The predicted crossover is negative.
- The crossover is outside the supported range.
- The model predicts no useful crossover in the tested range.
- The measurements are too noisy to support a reliable estimate.

Do not blindly extrapolate beyond measured workload sizes without clearly identifying the result as an extrapolation.

Explain the mathematical assumptions and the meaning of every fitted parameter.

## 11. Adaptive empirical search

Implement a search method that does not rely on the linear formula being correct.

Use geometric sampling and adaptive refinement.

The method should:

1. Start with a configurable workload size.
2. Increase sizes geometrically to explore a wide range.
3. Respect a configurable maximum workload size and measurement budget.
4. Repeat measurements and summarize timing variability.
5. Identify intervals where the CPU/GPU performance relationship changes or is uncertain.
6. Allocate more measurements to informative intervals.
7. Refine candidate boundaries.
8. Verify candidate crossover points using fresh measurements.
9. Report uncertainty and stopping conditions.

Do not assume there must be exactly one crossover.

If performance is non-monotonic, inspect the sampled regions and report any observed transitions the measurement budget supports. Do not claim to have found every crossover if the sampling could have missed one.

If the GPU never becomes consistently faster within the tested range, report that result honestly.

Respect workload constraints such as matrix dimensions and supported input sizes.

Use simple, understandable search logic. Explain the algorithm in the documentation.
